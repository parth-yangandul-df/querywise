QueryWise Platform Architecture

A full-stack text-to-SQL platform that lets people ask business questions in plain language, enriches each question with database and business context, generates or reuses safe SQL, executes it against connected databases, and returns a human-readable answer.

Python 3.12 · FastAPI React 19 Admin UI · Angular 21 Chat UI PostgreSQL · SQL Server · pgvector Anthropic · OpenAI · OpenRouter · Groq · Ollama LangGraph · Semantic Layer · Docker Compose

System Overview

QueryWise is organized into five logical layers. A user's question starts in either the Angular chat UI or React admin UI, enters the FastAPI backend, is routed through a LangGraph conversation pipeline, is enriched by the semantic layer, then runs through a connector against the selected target database. The same pipeline also persists chat sessions, query history, result previews, and follow-up context so later turns can build on earlier answers.

Semantic Layer Core IP

The semantic layer is the business context engine. It turns raw database metadata, business terms, metric definitions, sample queries, value dictionaries, and imported documentation into a compact prompt that the SQL composer can use. It combines vector similarity, keyword scoring, relationship expansion, glossary resolution, metric resolution, knowledge retrieval, and RBAC scope constraints so the LLM sees the right tables and business rules instead of the whole database.

Context Building Pipeline (11 Steps)

1 Embed Question
Generate vector via OpenAI text-embedding-3-small (1536-dim) or Ollama nomic-embed-text (768-dim)
2 Find Relevant Tables
Hybrid table discovery combines pgvector similarity with keyword matching against table names, column names, and comments
3 Resolve Glossary Terms
Match business terms by text and embeddings, then attach definitions, SQL expressions, and related tables
4 Inject Glossary-Linked Tables
If a matched term points to a table that was not discovered yet, add it so business language can pull in the right schema
5 Resolve Metrics
Find named calculations and dimensions so questions like revenue, utilization, or margin use the governed definition
6 Retrieve Knowledge Chunks
Search imported text, HTML, and URL documents for policies, definitions, or domain rules related to the question
7 Find Similar Sample Queries
Retrieve up to 3 validated NL-to-SQL examples; high-similarity examples can also become a trusted shortcut later in the graph
8 Infer and Expand Relationships
Use declared relationships and foreign-key neighbours to include likely join paths, scored against the question
9 Load Dictionaries
Add value mappings for selected columns so coded values and business labels are interpreted correctly
10 Apply Scope Constraints
When the user has a resource or employee scope, prepend deterministic instructions and skip unsafe shortcuts
11 Assemble Prompt
Format into structured sections: schema, relationships, glossary, metrics, knowledge, dictionary, examples, and constraints

Relevance Scoring Formula

relevance = semantic match + keyword match + business-term boost + relationship fit

Semantic Metadata Types

Business Glossary

Maps business terms to SQL expressions. Matched by substring + embedding similarity.

Metric Definitions

Named calculations with aggregation types and dimensions. Matched by name + embedding.

Data Dictionary

Column value mappings so the LLM understands coded values.

Knowledge Base

Imported documentation (wikis, HTML pages) chunked and embedded for semantic retrieval. Top 5 chunks injected as === BUSINESS KNOWLEDGE ===

Sample Queries

Validated NL→SQL pairs used as few-shot examples, and as trusted SQL shortcuts when similarity is high and scope rules allow it.

LLM Orchestration Layer

The core intelligence pipeline is a LangGraph StateGraph compiled as a singleton. It is no longer the older intent-template router. Instead, it is a multi-turn conversation workflow that loads prior context, resolves what the user is asking for now, chooses the right path, validates SQL before execution, retries correctable failures, interprets results, and writes an auditable history record.

LangGraph Graph Topology

load_history
  → resolve_turn
     ├─ query                         → build_context → similarity_check
     │                                                ├─ trusted sample SQL → execute_sql
     │                                                └─ compose_sql → validate_sql
     ├─ follow_up_query_refinement    → handle_follow_up → validate_sql or write_history
     ├─ show_sql / explain_result     → answer_from_state
     └─ clarification                 → write_history

validate_sql → execute_sql or handle_error
handle_error → validate_sql / execute_sql / write_history
execute_sql  → interpret_result or handle_error
interpret_result → write_history → END

Graph Nodes

load_history

Loads recent session messages plus the last successful query context from query_executions.

This gives the graph enough memory to answer "show the SQL", "explain that result", or follow-up refinements.

resolve_turn

Classifies the message as a fresh query, follow-up refinement, show-SQL request, result explanation, or clarification.

It also rewrites follow-up wording into a standalone resolved question when needed.

build_context

Calls the semantic context builder to gather schema, glossary, metrics, knowledge, dictionaries, examples, and access-scope constraints.

similarity_check

Compares the question to validated sample queries. A high-confidence match can reuse trusted stored SQL and skip composition.

Shortcuts are skipped when user scope constraints make reuse unsafe.

compose_sql & validate_sql

The composer generates SQL from the resolved question and semantic prompt. The validator checks SQL safety and schema references before anything runs.

execute, interpret, write

The connector executes read-only SQL, the interpreter writes the plain-English answer, and write_history saves SQL, preview rows, summary, status, and turn context.

Turn Actions

query

Fresh database question. Build semantic context, compose or reuse SQL, validate, execute, interpret.

follow_up_query_refinement

Uses prior turn context. Can reuse an answer, rewrite SQL, or escalate back to full context building.

show_sql

Returns the last generated or executed SQL from saved state without querying the database again.

explain_result / clarification

Explains a prior result from preview data, or asks the user to clarify when the request is not safe or specific enough.

The optional follow-up path is controlled by USE_FOLLOW_UP_PATH. When disabled, ambiguous follow-ups fall back to the normal query path or clarification behavior.

Role-Based Model Routing

RolePurposeTypical Model Setting
Resolver Turn classification, follow-up detection, and resolved-question rewrite RESOLVER_MODEL when using OpenRouter
Composer SQL generation and correction using semantic context DEFAULT_LLM_MODEL or OPENROUTER_MODEL
Interpreter Convert rows into a concise answer, highlights, and suggested follow-ups INTERPRETER_MODEL
All provider calls use temperature 0.0 for deterministic behavior. OpenRouter can split resolver, composer, and interpreter roles across different configured models.

Specialized Agents

QueryComposerAgent

Input: Resolved question + assembled semantic context

Output: SQL + explanation + confidence (0–1) + tables_used + assumptions

Response: JSON parse with regex fallback for code-fenced SQL

SQLValidatorAgent

Level 1: Static regex blocklist (DROP, DELETE, INSERT, ALTER, CREATE, TRUNCATE, pg_sleep, etc.)

Level 2: Schema reference check via sqlparse (tables/columns exist)

Status: VALID | UNSAFE | SYNTAX_ERROR | SCHEMA_MISMATCH

ResultInterpreterAgent

Input: Question + SQL + results preview (max 20 rows)

Output: NL summary + key highlights + suggested follow-up questions

Empty rows: Returns an explicit "No matching rows found." response.

ErrorHandlerAgent

Trigger: Validation failure OR database execution error

Input: Failed SQL + error + schema context + previous attempts

Output: Corrected SQL + explanation + should_retry flag

Max retries: 3

Embedding resolution: Embeddings can come from OpenAI, Ollama, or an explicit EMBEDDING_PROVIDER. If embeddings are unavailable, parts of the semantic layer degrade to keyword-oriented retrieval instead of failing the whole query.

Connector Layer

A plugin system for database connectivity. All connectors implement BaseConnector, are resolved through connector_registry.py, and are cached by connection ID with stale-connection cleanup. The connector layer is where read-only execution, timeouts, row limits, schema introspection, and sample value lookup meet the real target database.

BaseConnector Interface

class BaseConnector(ABC):
    connector_type: ConnectorType

    async def connect(connection_string: str, **kwargs) -> None
    async def disconnect() -> None
    async def test_connection() -> bool
    async def introspect_schemas() -> list[str]
    async def introspect_tables(schema="public") -> list[TableInfo]
    async def execute_query(sql, params, timeout_seconds=30, max_rows=1000) -> QueryResult
    async def get_sample_values(schema, table, column, limit=20) -> list[Any]

Query Flow Pipeline

End-to-end flow when a user submits a natural language question through POST /api/v1/query or POST /api/v1/query/stream. The client sends the selected connection, the question, and optionally a session_id. The backend owns conversation history and loads it from stored executions.

Standard Query Path

1 User submits NL question
"Show revenue by client this quarter" — with connection_id, optional session_id, and optional clear_context flag
2 query_service builds GraphState
Loads the connection, decrypts its connection string, injects auth scope, max rows, timeout, session ID, and streaming queue
3 load_history → resolve_turn
Loads recent persisted turns and decides whether this is a fresh query, follow-up, show-SQL request, explanation request, or clarification
4 build_context → similarity_check
Assembles semantic context. If a validated sample query is a safe high-confidence match, its stored SQL can be reused directly.
5 compose_sql → validate_sql
If no trusted shortcut is used, the composer generates SQL and the validator checks safety and schema references before execution.
6 execute_sql via Connector
Runs read-only SQL with timeout and row limit. Validation or database failures route to handle_error for correction retries.
7 interpret_result → write_history
Creates a plain-English answer, highlights, and follow-ups. Persists SQL, preview rows, result_status, retry count, and turn context.

Follow-Up and State-Aware Path

1 User submits NL question
"Now only show last month" or "show me the SQL" — the client sends the same session_id
2 load_history
Fetches compact prior context: resolved question, SQL, answer, columns, result preview rows, and result_status
3 resolve_turn
Chooses between reuse_answer, rewrite_sql, needs_full_compose, show_sql, explain_result, or clarification
4 handle_follow_up or answer_from_state
Reuses cached answer, sends rewritten SQL through validation, answers from saved state, or escalates to the full context path
5 Validation still applies
Even rewritten follow-up SQL must pass the same SQL safety and schema validation as a fresh query
If ambiguous, ask a clarification instead of guessing
6 execute_sql when needed
Only database-changing follow-ups rerun SQL; show-SQL and explain-result turns can be answered from stored context
7 interpret_result → write_history
The new turn is persisted so the next message has a reliable state trail to work from

Security Architecture

Defense-in-depth strategy with multiple independent safety layers, ensuring no single bypass can allow destructive operations.

🔒

Read-Only Enforcement

PostgreSQL uses read-only transactions. SQL Server support runs through the connector interface and still passes through shared safety checks before execution.

🚫

SQL Blocklist

Static regex patterns block DDL, DML, admin commands, multi-statement payloads, and dangerous functions such as pg_sleep, xp_cmdshell, OPENROWSET, and bulk operations.

🔑

Encrypted Credentials

Connection strings encrypted at rest with Fernet (AES-128-CBC). Never returned in API responses — only has_connection_string: boolean.

⏱

Statement Timeout

Each connection carries its own max query timeout. PostgreSQL sets statement_timeout; connector implementations enforce equivalent limits where available.

📊

Row Limits

Auto-wrapping queries with LIMIT N+1 to cap result size. Default 1,000 rows, configurable per connection. Truncation flag in response.

🌐

CORS Restriction

FastAPI CORS middleware restricts origins. Development defaults include the React admin UI, Angular chat UI, and configured local ports.

Plain-English Architecture

What the System Does

QueryWise is a controlled translator between business language and database language. A person asks a question, the system looks up the relevant business definitions and database structure, writes safe SQL, runs it, and explains the answer in normal language.

Why the Layers Matter

The UI gives users a place to ask and review. The API validates requests. LangGraph manages the conversation. The semantic layer supplies business context. The connector safely talks to databases. The metadata database remembers what happened for audit and follow-up questions.

How Follow-Ups Work

The user does not need to repeat everything. The backend stores compact context from prior successful turns, so "show me the SQL", "explain that", or "now only last month" can refer to the previous answer.

How Risk Is Reduced

The system avoids blindly running generated SQL. It checks for dangerous statements, validates schema references, applies row and timeout limits, enforces user scope, and stores a history trail of SQL, results, status, and retries.
